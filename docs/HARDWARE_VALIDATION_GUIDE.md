# Hardware validation guide — replacing the mocked steps in this PR

This deployment run (`run-7d942761`) was produced without a physical board
connected. Host parity is real and passing; **device parity** and
**benchmark** are mocked. If you have the Arduino UNO Q (STM32U585) in
hand, here's how to replace them with real data.

## 0. Prerequisites

- `arduino-cli` installed, with the `arduino:zephyr` core (`arduino-cli core
  list` should show it).
- The board connected over USB. Find its serial port:
  - Windows: Device Manager -> Ports (COM & LPT), or `arduino-cli board list`
  - macOS/Linux: `ls /dev/tty.usb*` or `/dev/ttyACM*` / `/dev/ttyUSB*`
- Python deps: `pip install -r mcp_server/requirements.txt` (includes
  `pyserial`, needed by `tools/target/benchmark_target.py`).

**Port is currently hardcoded to `COM3`** in
`mcp_server/adapters/target_adapter.py`'s `run_benchmark_target` (the
`port="COM3"` argument to `run_physical_benchmark`). If your board isn't on
`COM3`, edit that line before running the benchmark step below.

## 1. Device parity (real)

The existing single-sample smoke test:

```bash
python tools/target/run_device_parity.py
```

This flashes the benchmark harness sketch, sends the frozen `yes.wav`
fixture, reads back the on-device tensor over UART, and compares it to the
frozen PyTorch reference. It writes
`evidence/parity/device_parity_report.json` (this is what's already in the
repo — re-running it overwrites it with a fresh timestamp but the same
comparison).

To get real data into **this deploy branch's** `run_parity_test_tool`
output instead of the mock:

```python
import asyncio, os
os.environ["CODE2EDGE_RUN_PARITY_TEST_MODE"] = "real"
```

...but note: **`run_parity_test`'s adapter doesn't have a real-mode
implementation for `gate="device"` yet** (`mcp_server/adapters/pipeline_adapter.py`
raises `NotImplementedError` for it — see `docs/interface-requests.md`).
Today, the only way to get a real device-parity number into this deploy
branch is:

1. Run `tools/target/run_device_parity.py` for real (above).
2. Manually copy the resulting `evidence/parity/device_parity_report.json`
   into `workflow/runs/run-7d942761/parity_device_attempt1.json`, noting
   in a commit message that it's a single-sample result, not a corpus sweep
   (until someone wires a real adapter for this gate).

**Stretch goal**: the device parity harness currently only tests one
fixture (`yes.wav`). A full corpus-wide device parity sweep (like the host
side's 500 samples) would need the on-device runner to loop over multiple
fixtures and report per-sample results — not done yet.

## 2. Benchmark (real)

Once the board is connected and the port is correct, call the MCP tool for
real:

```python
import asyncio, os
os.environ["CODE2EDGE_BENCHMARK_TARGET_MODE"] = "real"

from mcp_server.tools import benchmark_target

async def main():
    return await benchmark_target.run(
        model_file="src/pipeline/model_data.c",  # falls back to the
                                                   # documented 168.2 KB size
        n_inferences=100,
        target_id="STM32U585",
    )

result = asyncio.run(main())
print(result)
```

This compiles `tests/firmware/benchmark_harness`, flashes it, runs 100
timed inferences over serial, and writes
`evidence/benchmarks/stm32u585_benchmark_report.json`. Expect it to take a
few minutes (compile + flash + serial round-trips).

**`predicted_vs_measured`'s `latency_ms_mean` and `flash_used_kb` rows will
say `"predicted": "not estimated"`** — there's no design-time estimate for
those anywhere in the repo yet (see `docs/interface-requests.md`). Only
`sram_peak_kb` has a real prediction (from `check_target`'s arena sizing).
If you have or can derive a real latency/flash estimate, that's an open
gap worth closing.
