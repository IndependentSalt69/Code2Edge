# Code2Edge deployment workflow — Bob execution spec

This is the canonical spec Bob follows for one end-to-end deployment run.
It is the runtime counterpart to [docs/workflow.md](../docs/workflow.md) (the
project's high-level pitch of the same pipeline) — this file is what an
agent actually executes, step by step, tool call by tool call.

Read [.bob/rules/person-c-guardrails.md](../.bob/rules/person-c-guardrails.md)
first and follow it for every git action taken during a run.

Real repo paths referenced below (per [docs/workflow.md](../docs/workflow.md)):
`reference/tiny-kws/`, `reference/golden/`, `src/inference/`, `src/parity/`,
`src/pipeline/` (Person A), `src/firmware/`, `tools/target/` (Person B),
`contracts/target/` (Person B's schemas). All of these are **read-only** to
this workflow — see the guardrails file for the full read-only list.

---

## a. Start the run

Call `start_run_tool(requested_by="<who/what started this>")`. Remember the
returned `run_id` — every subsequent tool call in this run passes it.

## b. Analysis

Trace the preprocessing chain across `src/pipeline/`, `src/inference/` and
`reference/tiny-kws/`: list each stage with its source file, function and
constants (sample rate, window/hop length, FFT size, mel bands, etc).

Then call:
- `profile_model_tool`
- `inspect_pipeline_tool`
- `check_target_tool`

Run these as parallel subtasks if this Bob build's Orchestrator mode
supports it; otherwise run them sequentially and say so in the Edge
Readiness Report.

## c. Edge Readiness Report

Write `workflow/runs/<run_id>/edge_readiness.md`:
- Fits STM32U585 memory budget or not, and headroom
- Unsupported ops (from `check_target_tool`)
- Pipeline constants found (from `inspect_pipeline_tool`)
- Risks

## d. HUMAN CHECKPOINT

Show the Edge Readiness Report, then **stop** and ask the human to reply
`APPROVE` or `REJECT`. Never approve on the human's behalf. Call
`record_approval_tool(run_id=..., checkpoint="edge_readiness", approved=..., approver=..., notes=...)`
with their answer.

Generation (step e) calls `workflow.approval.assert_generation_approved(run_id)`
before writing anything — it raises `ApprovalRequiredError` if this
checkpoint was never APPROVEd, or was last REJECTed.

## e. Generation

Create an isolated worktree:

```bash
git worktree add ../code2edge-deploy -b deploy/kws-stm32u585-<run_id> origin/main
```

Write generated C/C++ **only** inside `../code2edge-deploy/deploy/`. Never
touch this branch's own `src/pipeline/`, `src/firmware/` or `deploy/` —
those are Person A's and Person B's live source, and the guardrails forbid
writing there even on `person-c/work`.

## f. Host parity gate

Call `run_parity_test_tool(gate="host", attempt=<n>, ...)` against the
generated code in the worktree, then
`gate_step_tool(run_id=..., gate="host", parity_result=<result>)`.

- `decision == "repair"`: change **only** the generated code for
  `focus_stage`, explain the change, increment `attempt`, and retry from
  the top of this step. The 3-attempt cap is enforced by `gate_step_tool`
  itself (`workflow/gates.py`), not by this loop — trust its `decision`.
- `decision == "continue"`: proceed to step g.
- `decision == "escalate"`: **stop**. Show the human
  `escalation_report_path` from the response
  (`workflow/runs/<run_id>/escalation_host.md`).

## g. MCU build and device parity gate

Build with Person B's tooling (`tools/target/`, `arduino-cli`,
`arduino:zephyr:unoq`) — read-only use, never modify those files.

Run the same gate loop as step f, with `gate="device"`.

## h. Benchmark

Call `benchmark_target_tool`, then write the predicted-vs-measured table
(predicted from `check_target_tool`/`profile_model_tool`, measured from
`benchmark_target_tool`) into the run's artifacts.

## i. Commit and PR (worktree only)

Inside `../code2edge-deploy` only:
- Commit in small Conventional Commits. Every commit body includes the
  line `Generated by IBM Bob via Code2Edge workflow, run <run_id>`.
- Push the deploy branch: `git push -u origin deploy/kws-stm32u585-<run_id>`
- Open a PR into `main`. Use Bob's own PR-generation feature if this build
  has one; otherwise `gh pr create`; otherwise give the human the compare
  URL and a PR body to paste.

## j. Rules during a run

- `mock_scenario` is used only when the human explicitly asks for a mock
  rehearsal. It is never used silently in a real run.
- Every report and artifact states whether its data was mock or real —
  read the `source` field on every tool output (`"mock"` | `"real"`).
- Escalation always stops the run for human debugging. Never retry past
  the cap yourself, and never treat an `"escalate"` decision as anything
  but a hard stop.

## Custom mode

**"Code2Edge Deploy"**: I looked for a per-project custom-mode config in
this repo (`.bob/custom_modes.yaml`, `.bob/modes.json`, or similar) and
found none — only `.bob/rules-agent/AGENTS.md`, `.bob/rules-ask/AGENTS.md`
and `.bob/rules-plan/AGENTS.md`, which are Bob's three *built-in* modes
(Agent/Ask/Plan), not a mechanism for defining a new named mode. I could
not confirm from the repo alone whether this Bob build supports creating
a custom mode at all — that has to be checked in Bob's own Settings →
Modes UI. If it does, point it at this file (`workflow/WORKFLOW.md`) as
its instructions, and — if the build supports scoping a mode's file edits
— restrict it to `../code2edge-deploy/deploy/` and `workflow/runs/`.

## Fallback (no custom mode available)

Paste this into Orchestrator (or Agent) mode to run a deployment:

```text
Read .bob/rules/person-c-guardrails.md and follow it strictly.
Execute the Code2Edge deployment workflow defined in workflow/WORKFLOW.md,
step by step, exactly as written there. Stop at the human checkpoint
(step d) and wait for APPROVE or REJECT before generation. On any
"escalate" gate decision, stop and show the escalation report instead of
continuing. Do not write generated code anywhere except
../code2edge-deploy/deploy/.
```
